# 组织转换端口化设计

组织模块剩下的 8 个转换是**唯一还集中写状态的规则**。本文给出把它们拆成「纯判定 + 纯条款 + 常量」
三层、同时不破坏 `transitions.ts` 守卫的设计。**先设计后动手**：设计里每一格都要能落成一条可断言的行为。

## 1. 现状盘点

`js/engine/organization.js` 共 328 行，其中纯查询已迁走（状态窗口、薪资倍率、无薪/口粮、晋升与联络
资格）。剩下的是：

| # | 转换 | 写入的状态 | 依赖的端口 | 调用方 |
| --- | --- | --- | --- | --- |
| 1 | `joinOrganization` | `job`、`opClass/opRank`、`affiliation/orgRoute/orgRank/orgService/orgJoinedAt/orgJob/orgLastServiceYear`、`orgHistory[]`、`flags['org_'+id]`、`flags.lastJob`、`arts`（整合运动）、`city`（新沃尔西尼）、`income` | `organizationEligibility`、`OP_CLASSES`、`pick`、`organizationName`、`computeIncome` | 面试通过、转职抉择、`syncOrganization` |
| 2 | `leaveOrganization` | `orgHistory[]`、`retirementPension`、`flags['org_'+id]`、`flags.reunion/reunionLeft`、`opClass/opRank`、`job`、`orgCooldowns`、全部 `affiliation/*` 字段、`income` | `EMPLOYMENT_MODELS.retirement`、`NATION_BY_ID.ppp` | 辞退、劳役、退役、`syncOrganization`、转职 |
| 3 | `retire` | `flags.retired`、`flags.lastJob`、`job`、`retirementPension.suspendedAt/resumedAt` | `isWorking` | 年度结算、玩家操作 |
| 4 | `syncOrganization` | `orgSchema`、`orgJob`、`orgRank`（其余通过 2 触发） | 状态窗口、`locationAllowed`、`nations` | 每年 `organizationYear`、`endYear` |
| 5 | `promoteOrganization` | `orgRank`、`orgLastPromotionYear`、`opRank`（罗得岛）、`orgHistory.ranks/promotions`、`income` | `organizationPromotionReady` | 年度复核 |
| 6 | `organizationContact` | `orgContacts[id]`、`eff` | `organizationContactEligible` | 组织事件 |
| 7 | `beginOrganizationInterview` / `completeOrganizationInterview` | `orgApplicationSerial`、`orgApplication`、`orgCooldowns`、`flags['org_transition_'+id]` | `organizationEligibility`、评分适配器 | 招募、剧情 |
| 8 | `dismissFromJob` / `enterCoercedLabour` | `job`、`flags.lastJob`、`flags.retired`、`retirementPension.suspendedAt`、`flags.slaveAt` | `isWorking` | 事件效果 |

另外还有一处**准入判定**没被算进这 8 个，但它是这里最重的规则：`organizationEligibility`（14 道检查、
300 行里的 28 行、被 6 处调用、34 条路线 × 21 国都要过）。

## 2. 三层拆分

### A 层：判定（纯函数，返回结论而不是改状态）

```ts
type Verdict = {ok: true} | {ok: false; code: VerdictCode; reason: string};

canBeDismissed(subject, env): boolean
admissionVerdict(subject, target, context, ports): Verdict   // 原 organizationEligibility
coercedLabourGuard(subject, job): Verdict                    // 能否押走、是否已在该岗位
retirementGuard(subject): Verdict                            // 年龄/阶段/是否已退役
syncVerdict(subject, org, route, ports): Verdict             // 离职原因与选项，或 update
applicationVerdict(state, application, ports): Verdict        // 跨年、任职关系变化、再走准入门槛
```

`Reason` 与 `VerdictCode` 都用**字面量联合**，因为 `code` 已被 `tools/verify-organizations.mjs` 与
legacy 调用方当作行为断言（`'closed' | 'age' | 'education' | ...`）；`reason` 是给 UI 的中文文案，
仍允许从内容侧传入。

### B 层：效果条款（纯数据，不碰状态）

```ts
pensionTerms(finalMonthlyPay, serviceYears, rank, policy, nationPpp): PensionTerms | null
leaveTerms(subject, reason, options, ports): LeaveTerms
   // { pension: PensionTerms|null, clearsOperatorRank: boolean, resetsJob: boolean,
   //   cooldownYear: number, keepsJob: boolean }
promotionTerms(subject): {rank: number; mirrorsOperatorRank: boolean}
contactRecord(previous: ContactRecord|null, contact: ContactDef, year: number): ContactRecord
```

这一层的价值在于**顺序即语义**：现在"先记历史、再核退休金、再清旗标、再清职级、再清岗位、最后写冷却"
的顺序藏在函数体里，任何人重排都会静默改变结果（例如先清岗位再核退休金，退休金就会按待业薪资算）。
把顺序固化成 `LeaveTerms` 的字段，legacy 只负责按既定顺序应用，顺序就成了可断言的对象。

### C 层：政策常量

`COOLDOWN_YEARS = 3`、`WAITLIST_YEARS = 1`（面试未决）、`CONTACT_LIMIT = 3`、`CONTACT_GAP = 4`
（后两个已在 `organization.ts`）。全部导出，测试直接引用常量而不是魔法数字。

## 3. 必须留在 legacy 的四件事

1. **所有状态写入**。判断在模型层，写入在装配层（与前面几轮一致：模型零副作用）。
2. **文案与时序日志**。`TL.log` 的句子、`key`、`kind` 参与快照，保持原样。
3. **`computeIncome` 的调用时机**。join/leave/promote 之后各调一次，且 join 内部先 `leave`（转职）
   再写新身份 —— 这个嵌套顺序会改变薪资与快照，不能搬到模型层。
4. **`syncOrganization` 的 `orgSchema === 1` 一次性迁移**。它是存档升级，不是规则。

## 4. 判定顺序表（顺序即语义）

`admissionVerdict` 必须保持现有 14 步的**先后次序**，因为 `code` 会随顺序变化，而事件与测试按 `code`
分支：

1. `unknown`（组织或岗位不存在）
2. `ended`（`phase !== 'life'`）
3. `closed`（当年不招募）
4. `location`（`def.locationAllowed` 为假）
5. `unavailable`（在学 / 已退休 / ≥65 / 服役中 / 劳役或退休职业）
6. `affiliated`（已有组织且非转职）
7. `cooldown`（`orgCooldowns[id] > year`）
8. `nation`（`def.nations` 不含本国；龙门卫队 + YAN + 龙门城 例外）
9. `age`（`route.minAge` / `maxAge`）
10. `route_year`（`route.fromYear`）
11. `education`（`route.edu`）
12. `profession`（`route.jobs` 不含当前职业时，待业者须满足目标职业的学历与技艺门槛）
13. `requirements`（`route.require(S)` 内容谓词）
14. `organization_requirements`（`def.require(S)` 内容谓词）

`syncVerdict` 的离职原因优先级同样固定：

```
档案失效 > 整合运动旧编制瓦解 > 地区禁令 > 退休/应征服役/结束任职 > 转行 > 迁出辖区
```

其中"退休/应征服役/结束任职"三者选一，且带不同的 `options`（`keepJob`、`retirement`、
`preserveOperatorRank`），这正是现在最容易写错的一处。

## 5. 风险清单

1. **`require` 是内容谓词**，读原始状态。端口签名必须是 `(state: unknown) => boolean`，与
   `oripathy` 的 `discrimination` 同样的处理；不要在模型里假装它是纯数据。
2. **`join` 会先 `leave`**（转职）：`admissionVerdict` 必须允许 `context.transfer` 通过，而实际的
   `leave` 顺序由 legacy 保持。
3. **退休金只生成一次**：`!S.retirementPension` 才生成，且只在 `retirement` 或 `reason === '退休'` 时。
   重复生成会覆盖已经停发/恢复记录的老退休金。
4. **停发/恢复是两条路径**：劳役时打 `suspendedAt`，退休时转成 `resumedAt` 并删掉 `suspendedAt`。
   金额永远沿用当年核定的数字，不重算。
5. **`opRank` 与 `orgRank` 的双向镜像**只对罗得岛成立，且 `preserveOperatorRank` 会关掉清空。
6. **快照一致性**：`report.orgHistory` 是快照，转换必须写入状态而不是改报告对象。

## 6. 落地顺序（每步都要有独立证据）

| 步 | 内容 | 证据 |
| --- | --- | --- |
| 1 | `admissionVerdict` 类型化，但**先不接线**：模型与 legacy 的 `organizationEligibility` 并存 | 差分探针：随机状态 × 34 路线 × 21 国，逐条比对 `ok/code`（含 14 步全部短路点） |
| 2 | 接线 `admissionVerdict`，legacy 只做调用 | 42 局兼容样本 + `verify-organizations`（34 路线 × 全体准入断言）+ 上一步的差分探针改成对同一函数 |
| 3 | `pensionTerms` / `leaveTerms` / `promotionTerms` / `contactRecord` 类型化，legacy 按顺序应用 | 退养金金额、冷却年份、职级重置、联络计数的单元测试；`verify-organizations` 的离职/退役段落 |
| 4 | `syncVerdict` 与 `canBeDismissed` / `coercedLabourGuard` / `retirementGuard` | 离职原因优先级表逐格断言；劳役与退休金停发的交叉用例 |

**差分探针是这一步的关键**：第 1 步让新旧两份实现同时存在，用几千个随机状态比对 `ok` 与 `code`，
把"我以为等价"变成"逐条相等"。这比等兼容样本报哈希要早得多，也精确得多（哈希只告诉你哪一局变了）。

## 7. 明确不做

- 不重写岗位推断（`r.entryJob` / `r.jobs[0]` / `op_<class>` 的既有优先级）。
- 不改整合运动的技艺加成（+8）与新沃尔西尼的城市改写。
- 不动任何日志文案与 `key`。
- 不把 `retire` 的 `deferOrganizationExit` 语义改成别的顺序 —— 年度结算是先退休、后由
  `syncOrganization` 结束组织身份，这个延迟是有意的（见 `year.js` 的注释）。
