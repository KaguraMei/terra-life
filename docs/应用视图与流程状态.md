# 应用视图与流程状态

`LifeView` 回答"这个人是谁"。流程层（`js/main.js`）要回答的是另一个问题：
**"这一局现在走到哪、玩家在做什么"**。把两者混成一个万能对象是常见错误 —— 于是有了独立的
`SessionView`。

## 两个视图的边界

| 视图 | 回答 | 谁写 |
| --- | --- | --- |
| `deriveLifeView(S)` | 姓名、身份、健康、职业、经济、家庭、日志、场景…… | 只有模型与内容层写；视图只读 |
| `deriveSessionView(S)` | 阶段（life/report）、年龄、播放节奏、是否有待决抉择、种子 | 播放控制由**玩家**写（暂停、倍速、重心），视图只读 |

`SessionView` 的形状：

```ts
{
  phase: 'life' | 'report' | 'other',
  age: number,
  pacing: {progress: number, yearSeconds: number, paused: boolean, speed: number},
  decision: {open: boolean, id: string | null},
  seed: number | null
}
```

两点刻意的取舍：

1. **节奏仍然留在状态对象上**（`S.t`/`S.yearSec`/`S.paused`/`S.speed` 是写操作）。视图只负责把它们读出来，
   这样将来把节奏移出状态对象时，改的是 `session-view.ts` 一处，而不是每个调用点。
2. **`decision.open` 不携带抉择本身**。弹层需要 `pending` 的标题、正文与选项，那是内容对象，
   由流程层原样传回给 `TL.showDecision`；视图只回答"要不要拦住时间"。
3. **不推导"哪一屏"**。屏幕是流程状态机（开局 / 掷签 / 游戏 / 报告 / 存档），由 `main.js` 的
   `hidden` 切换与 `UI` 变量决定，硬塞进视图只会让视图依赖 DOM。

## 迁移结果

`js/main.js` 的直读从 **52 行降到 17 行**，剩余部分是：

| 剩余 | 性质 |
| --- | --- |
| `S.paused` / `S.speed` / `S.focus` / `S.pending` 的**写** | 玩家操作，理应写 |
| `S.pending` 对象本身传给 `TL.showDecision` | 弹层要的是内容对象，不是投影 |
| `S.report` / `S.lt`（报告屏内部） | 报告屏渲染自己的快照 |
| 存档行模板里的 `s.name` 等 | 变量名撞车，非状态读取 |

也就是说流程层现在只有"写节奏"与"把对象交给弹层"两类直接接触。

## 为什么先设计再动手

机械地把 52 处替换成视图调用，会得到第二个万能对象；先分清"人物事实 / 会话状态 / 屏幕状态机"三类，
才发现只有前两类适合投影，第三类必须留在流程层。真要做流程状态机建模，需要的是显式状态迁移
（landing → birth → game ⇄ report），那是另一个议题，不在视图层解决。
